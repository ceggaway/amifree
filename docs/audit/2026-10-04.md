## Conclusion

The existing suite passes, but additional simulations reproduced three defects. The MVP is not yet verified end to end against live services. Telegram authentication and Supabase table reads work. OpenAI is intentionally unconfigured; the current startup gate prevents polling/webhook startup without it.

## Confirmed findings

1. **High priority: mixed time formats can silently change the event time.** In `app/services/date_resolution.py:109`, the end time's AM/PM suffix is passed into start-time parsing even when the start is explicit 24-hour time. A structured extraction of `Friday 07:00 to 9pm` becomes 19:00–21:00 rather than 07:00–21:00. `19:00 to 9pm` instead raises a clarification. The wrong interval can miss daytime clashes. Preserve explicit 24-hour starts and inherit suffixes only for genuinely abbreviated starts. Reproduced directly against the validator with controlled extraction output; this does not claim what the live model will extract.

2. **Medium priority: future commitments become inaccessible through normal discovery after 30 days.** `app/db/supabase.py:123` filters by creation time, not event time. Both `/events` and natural-language update/cancel matching use this result (`app/services/scheduling.py:99` and `:176`). A future GOING event created 31 days ago is absent from discovery but still blocks availability. Reproduced using the real repository, Supabase SDK, and real PostgreSQL SQL in PGlite with simulated HTTP transport. Old Telegram cards can still access the record. The documented recent-event limit explains the behavior but does not provide a discovery route to all upcoming commitments. Include upcoming commitments and provide pagination or explicit lookup.

3. **Medium priority: a webhook can acknowledge an update that was neither processed nor reported to the user.** `app/bot/handlers.py:71` catches processing failures; the global error handler also consumes failures in sending the error response. `app/main.py:177` then returns HTTP 200. Injecting a database outage and a Telegram reply outage produced HTTP 200, no user record, and no reply. There is no durable retry recorded by this path. Propagate retryable failures to the delivery layer or persist an incoming update before acknowledging it, with idempotent replay handling. The probe uses actual FastAPI/PTB dispatch and simulated upstream failures. This finding concerns webhook mode; it is not a live outage test.

## Reproduce locally

Run from `amifree/`, with the existing virtual environment and optional SQL test dependencies installed:

```sh
.venv/bin/ruff check .
.venv/bin/ruff format --check .
.venv/bin/python -m compileall -q app scripts tests
.venv/bin/python -m pip check
.venv/bin/pytest -q --cov=app --cov-branch --cov-report=term-missing
npm --prefix scripts/sql-tests test
PYTHONPATH=. .venv/bin/python docs/audit/reproduce.py
.venv/bin/python scripts/smoke_backend.py
```

`reproduce.py` now asserts the corrected behavior. It uses local synthetic records and does not connect to production services.
